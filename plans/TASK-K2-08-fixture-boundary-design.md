## Decision requested

Review the bounded fixture boundary, four-scenario acceptance matrix, and rollout order below. The previous design at `66e85560d14f5529bc35fb52072779af293f473c` was NO-GO. This revision addresses its findings: master-only hosted execution follows source merge and migration; policy competition is split across four fresh actors; actor eligibility is proven before Today; the probe is a guaranteed-empty `HEAD` with `limit=0`; and raw `/v1/me` identity data remains runner-only.

The current function-based Auth/RLS proposal remains NO-GO. A non-owner function cannot inspect Auth metadata. This design uses only existing Auth Admin and service-role capabilities inside the protected server-side runner, with strict code-enforced, actor-bound operations. It adds no roles, grants, policies, functions, keys, signatures, endpoints, or Auth access rules. Production authorization and RLS remain unchanged.

## Privilege boundary and data flow

### Runner-private authority

The protected owner-dispatched runner alone retains the Supabase URL, service key, Auth Admin client, read-only acceptance reader, current-run actor UUIDs/emails/passwords, normal actor bearer tokens, language profile IDs, and raw API responses. The service key is never treated as an actor JWT. The Admin client uses supported Auth Admin SDK/API operations only; it does not query `auth.users` through SQL or PostgREST. Runner-private Supabase SDK operations are limited to the existing fixture INSERT and an exact actor/profile/concept-filtered read of the already-granted K2-05 view. The acceptance reader remains read-only for the catalog/base-candidate proof and cleanup/retained checks.

`runK2HostedWave` must stop passing the complete `K2HostedConfig` through `K2HostedWaveContext.config`. The wave receives no raw config, key, database URL, OIDC material, Admin/reader client, actor UUID, profile UUID, email, password, or bearer. Give it only runner-created opaque actor handles, bound normal-API closures, one closed fixture request handle per eligible fixture actor, sanitized proofs, and an allowlisted checkpoint sink.

### Actor operations and identity projection

Each bound product closure keeps its actor's ordinary Supabase session, fixed API origin, actor binding, and exact profile binding private. It accepts no caller-supplied bearer, actor ID, profile ID, route origin, or arbitrary path. It exposes only the reviewed existing product operations required by the wave and returns allowlisted projections.

The runner alone calls `/v1/me` during bootstrap and reads its raw response. It uses the UUID/profile fields internally to bind subsequent calls and verify ownership; no `/v1/me` payload or identity/profile UUID crosses into the wave. Other route responses that contain IDs are compared or mapped to opaque handles inside the runner. The wave receives an enum, boolean, bounded count, or opaque handle only. Assert this response projection with sentinels in tests; do not claim that the raw identity response is absent from the runner.

Admin/service credentials never appear in browser code, browser storage, Auth sign-in, actor-visible API requests, traces, screenshots, logs, assertions, annotations, reports, or workflow artifacts. The browser continues to use the existing publishable key and ordinary actor sign-in. Playwright trace, screenshots, and video remain disabled.

### Closed fixture and snapshot operations

The runner constructs fixture bindings only from its in-memory `createUser` results in the current process. The fixture helper supports exactly two scenario modes: `forgotten_weak_pair` for actor B and `weak_only` for actor C. Actor A and actor D receive no privileged fixture writes. No helper accepts caller-supplied actor/profile/concept UUIDs, table, SQL, columns, status, metadata, query predicate, conflict mode, or arbitrary payload.

Before fixture setup/readback, re-fetch that exact in-memory actor with Auth Admin `getUserById`; require exact current Auth UUID, reserved synthetic identity, server-owned app_metadata run marker, pinned project/repository/master workflow/run/attempt, creation timestamp, and unexpired bounded TTL. Ignore `user_metadata`. Also verify the exact current-run actor/profile/language association through the read-only reader with exact actor/profile predicates. Missing actor, metadata drift, wrong profile, expired marker, or reader failure blocks fixture setup/readback. Cleanup has a separate rule: re-fetch the exact in-memory Auth identity and revalidate its server-owned project/repository/workflow/run/attempt marker, identity ownership, and bounded TTL; if they match, delete that Auth identity and then prove Auth absence plus zero actor-owned residue. If it is already absent, proceed directly to residue proof; a mismatch or inconclusive Auth result fails closed. Do not gate deletion on whether profile bootstrap was reported as successful or whether a profile is visible before deletion: the profile POST may commit while its response is lost. This permits Auth cascade cleanup of a partial or response-ambiguous profile without selecting an arbitrary user or profile. Plugin code cannot request arbitrary snapshot selectors.

The fixed fixture helper issues INSERT only to `public.user_concept_states` for content-linked concepts selected from the already-reviewed published candidates. `forgotten_weak_pair` inserts exactly two rows, one weak and one forgotten; `weak_only` inserts exactly one weak row. Existing constraints/defaults remain active. Use the existing status vocabulary and minimum fields needed for candidate status; do not fabricate evidence, timestamps, mastery, confidence, exposure, review, or learning events. Never write `public.users`, `public.user_languages`, evidence, FSRS, competence, Reader, Library, Today, or catalog tables through this helper. No upsert/update/delete/truncate is permitted. Ambiguous insert response permits one exact same-invocation readback for that bound actor and fixed content pair; if the complete expected state is not proven, fail and delete the actor. Never overwrite or adopt a fixture in a later process.

The fixture inspector never calls `listUsers`, reads real learner rows, or selects by a caller-chosen actor. It returns only a fixed created/status-count proof. Current-run actor snapshots and cleanup counts are likewise filtered to the in-memory fresh actor set and projected to aggregates. Existing retained snapshots may continue the accepted 27-table read-only digest in process, with only digest/count equality escaping the runner.

Any failed proof prevents Today generation; the shared finalizer still removes any actors already created.

2. Through the existing read-only acceptance connection, verify the reviewed role/ACL/RLS/owner tuple and exact probe capabilities. 3. Send one fixed `HEAD` request to the pinned `public.user_concept_states` REST target using `limit=0`, with no filter, no count preference, and no body. It must return no row body. This formally requests zero rows while checking the pinned target and existing SELECT path; it is not evidence of INSERT. The read-only ACL metadata check proves the pre-existing INSERT grant. If the target rejects this exact request, stop; do not fall back to a random-UUID predicate, count, or row query.
4. Verify catalog readiness before creating actors. Require at least three distinct published Reader candidates that pass the existing human publication/provenance/license/level gates. A minimal source-rank shape is N first, W second, F third; W and F items must each estimate five minutes, and N must be eligible new curriculum. This permits B to mark the middle item weak and bottom item forgotten and C to mark the bottom item weak, using only actor-bound status rows. Fresh actors have no familiar/active/mastered states; `content/store.py` counts known concepts only for those statuses. Weak/forgotten fixture rows do not count as known, so each candidate must have at most four distinct linked concepts in total for a fresh actor. Do not treat passive exposure/discovered as familiar or bypass the unseen cap.
5. Ensure all due concepts for A/B are 20 distinct concepts established through the supported normal actor API and Review lifecycle, and disjoint from every concept linked to all eligible candidates, so due exclusion cannot remove a remediation candidate. Do not seed due state through the privileged fixture helper, alter clocks, or invent timestamps. Content readiness is presently false in staging. This design therefore authorizes no hosted run. ### Actor-specific candidate proof before Today

No new API route or grant is needed for the candidate proof. Extend the existing Python `tests/acceptance/support/k2_hosted_probe.py` using its SELECT-only acceptance connection and the same catalog/base-candidate authority as PR #35 `ContentStore.list_summaries` / `TodayStore.list_content_candidates`. Actor-owned relations (`user_languages`, `user_concept_states`, `user_saved_content`, `user_content_progress`, due relations) always carry exact actor/profile predicates; the catalog scan contains only published catalog data. The probe must not scan learner rows across users or select real learner rows. The acceptance reader cannot read the K2-05 retrievability view, so the reader probe must not query it or claim view-based status proof.

The reader probe also identifies candidate-linked concepts with an exact current actor/profile `user_concept_states` row. Only this finite intersection can have a retrievability-view row. For the approved fixture matrix, the state-bearing candidate set is exactly actor B's two inserted concepts, actor C's one inserted concept, and empty for A/D because their due concepts are disjoint from candidate mappings and they have no other candidate-linked state. Any unexpected candidate-linked actor state must be attributed to a supported setup operation, included in the bounded proof, or fail closed; do not widen to an all-learner scan. For a nonempty set, the runner makes one existing service-SDK GET of `public.v_learner_concept_retrievability` with a fixed projection: `user_language_id`, `concept_id`, `stored_status`, `effective_status`, `memory_state`, `due_at`, `last_review_at`, and `calculated_at`. The query always includes exact `user_id = currentFreshActor`, exact `user_language_id = currentProfile`, `concept_id IN (the reader-returned state-bearing candidate concepts)`, and a fixed result limit of three. No wildcard projection, caller filter, unbounded GET, or row logging. Validate that every returned row matches one requested profile/concept, no duplicate or foreign row appears, and all requested state-bearing concepts return their expected row. No other actor ID, Auth row, or concept outside this at-most-three-ID set is inspected.

The runner combines these bounded view results with the read-only ContentStore base projection inside process memory, using `effective_status` supplied by the existing view (never a duplicate decay formula) and the same candidate enrichment/order rules as the source. The implementation must prove the probe's source rank and classification match `TodayStore.list_content_candidates` for the same synthetic fixtures; the probe does not declare its own competing eligibility formula. It verifies each competitor's publication/profile fit, unseen count, due exclusion, remediation/novel status, duration, source rank, and expected winner before Today. The plugin receives only per-scenario booleans/counts and opaque candidate handles, never the candidate rows, concept IDs, status map, or Auth/profile identifiers. The query split is intentionally bounded even though `service_role` has broad authority; adversarial tests must prove the exact request predicates and finite concept list.

K2-05 `calculated_at` is `transaction_timestamp()` within the view read's own database transaction. The synthetic weak/forgotten rows have `last_seen_at = NULL`, no Review item or FSRS row, and their effective status therefore remains their stored base status across view requests. Treat `calculated_at` as that request's timestamp only; do not require equality with a separate runner timestamp or across requests, do not force a test clock, and do not claim that this synthetic fixture proves natural decay. The actual Today endpoint continues to use its own existing database transaction/as-of path.

## Cleanup, recovery, and zero-residue contract

Normal completion, assertion failure, timeout, API error, or fixture failure always enters the existing unconditional finalizer. It signs out ordinary sessions and re-fetches each exact current-process Auth identity. If the identity exists, the server-owned project/repository/workflow/run/attempt marker, ownership, and bounded TTL must match before Auth Admin deletes that exact user. If `getUserById` reports the exact in-memory identity absent, the finalizer proceeds to residue proof; a mismatch or inconclusive Auth error fails closed and leaves the existing marked-actor recovery path responsible. Neither branch consults profile-bootstrap success or requires a profile lookup. It then proves Auth absence, proves zero actor-owned rows across the existing actor-owned inventory, and compares the post-cleanup retained 27-table digest to the pre-run digest. This is required even if `/v1/me/languages` committed a profile but its response was lost and the runner has no profile UUID. A fixed sanitized failure replaces wave success if cleanup or digest proof fails. No raw IDs or row details enter artifacts.

After process death during actor creation, profile bootstrap, setup, or seed, the existing current-run marked-actor recovery path and TTL janitor remain responsible for deletion and zero-residue proof. Auth deletion cascades the associated profile/state rows as currently configured. Cleanup does not need to reconstruct a lost profile UUID. Fixture helpers do not enumerate Auth users or rediscover/adopt rows. Existing recovery uses `listUsers` because the API offers no verified exact run filter; preserve it as an isolated, inherited janitor, retain only minimum fields during pagination, ignore user_metadata, avoid complete-page retention and logging, and keep incomplete/ambiguous scans fail-closed. Do not broaden Auth grants or invent filtering semantics.

A recovery job after hard process loss can prove identity/row cleanup, but cannot recover the in-memory pre-run retained baseline. That run is permanently non-passing for K2-08 even if the janitor later clears all actors. A later complete run must capture a fresh baseline and satisfy all gates. Do not save IDs, rows, or retained snapshots as workflow artifacts to make a crashed run look complete.
